## 二·现在真正的痛（四条，都有今天的证据）

**P1　「摘要行契约」靠人记，不靠类型。**
每个 `check_*.py` 都要在末尾打印 `▸摘要:`，但没有任何机制强制。今天彩排抓到的两处 —— `check_week_coverage` 在文件不存在时 `return 2` 直接走人、`check_signals` 在参数解析失败时 `sys.exit(2)` 直接走人 —— **都是「有退出码、没摘要」**，入口那一行成了空白。契约只写在 AGENTS 第十节第四条里，写的人记得、改的人不一定记得。

**P2　退出码语义靠约定，不靠结构。**
0 通过／1 不合格／2 参数问题，三种语义挤在一个 `int` 里。于是 `check_week_coverage` 用 2 表示「文件不存在」，`run.py` 用 2 表示「没有脚本认领这个参数」——同一个 2 两种含义，体检的提示词只能额外写一段来解释「exit 2 有两种可能」。

**P3　同一判据出现在两处，改一处就漂。**
归档周豁免：`--all` 走推断、`--week` 没走（今天修的 B2）。黑名单：`check_docs` 与 `clean_sources` 曾各一份（10-25 合并前已漂移，`jiemian`/`xueqiu`/`guba` 三个域名只有一份有）。**这类事故在这个库出现了 5 次**，都是「同一件事写两遍」。

**P4　判定与打印混在一起，所以没法测。**
`check_*` 里既有「比什么」又有「怎么印」。想给「模板行匹配」「八字段完整度」写个单测，得先捕获 stdout 再解析字符串——目前 **0 个测试**，全靠 `run.py check` 的退出码兜。

## 四·四条依赖规则（这才是「模块化」，其余只是搬文件）

1. **方向单向**：`run.py → actions → checks → domain → core`。低层不许 import 高层；`core` 里不许出现**口径**（名单／枚举／判据），但可以有**目录名与结构名**（`wiki/政策卡片`、`### 日期 · 标题`）——前者是「规则是什么」，后者是「数据在哪」。2026-10-25 修订：原措辞是「不许知道『政策』两个字」，会与必需的目录名冲突，而判据本来就该按**是否含口径**判，不是按字面词判。
2. **checks 只判定，不打印**：每个 check 返回 `Result`，明细行放在 `Result.lines` 里。`--only`／`--full`／摘要三种输出**由 `actions/check.py` 一层决定**——今天这个逻辑散在 run.py 的 `pick_summary()` 和各脚本的 `verbose` 参数里。
3. **口径单源**：任何「名单」「枚举」「判据」只能住在 `domain/`。`check_*` 里出现字面量 `'2026-W40'`、`'金融强国'`、`'jiemian.com'` 都算违规，由 `check_docs` 加一条扫描来守。
4. **一个文件一个可测单元**：`pkb/**/*.py` 的每个模块都能被 `python3 -c "import pkb.checks.weeks"` 单独导入，且导入时不读盘、不打印。

## 五·退出码改成可读的枚举（P1、P2 的正解）

```python
# core/report.py
class Verdict(Enum):
    PASS       = 0    # 通过
    FAIL       = 1    # 有问题，必须处置
    BAD_INPUT  = 2    # 参数/输入缺失，结论不成立
    SKIP       = 3    # 按规则豁免（归档周等），不计入

@dataclass
class Result:
    verdict: Verdict
    summary: str          # 一行，就是现在的 ▸摘要
    lines: list[str] = field(default_factory=list)   # 明细，--only 才打印
```

`run.py` 只做一次映射：聚合取 `max(verdict)`，`SKIP` 不参与；`BAD_INPUT` 单独提示「本次结论不含该范围」。**「有退出码没摘要」从此写不出来**——`Result.summary` 没有默认值，不填就构造失败。

## 六·迁移五步（每步都有验收门槛）

> 前提：这个库没有 git。**第一步之前先把 `tools/` 整体拷到 `归档/备份/政策库备份-20261025-模块化前/`（约 140K）**，回滚就是拷回来。

| 步 | 内容 | 验收门槛（必须全过才进下一步） |
|---|---|---|
| 1 | `lib.py` 拆成 `pkb/core/*`，`lib.py` 留成 `from pkb.core import *` 的 6 行兼容层。**所有脚本一行不改。** | ① `run.py check` 输出与迁移前**逐行 diff 为空**；② `run.py export` 后 `check_docs` 0 硬错误 |
| 2 | 口径迁 `pkb/domain/`：黑名单、15 链判据、`LEGACY_WEEKS`、五领域枚举。删掉兼容层里的同名常量。 | ① 同上 diff 为空；② `grep -rn "'2026-W4[0-3]'"` 只命中 `domain/legacy.py`；③ `grep -rn "jiemian"` 只命中 `domain/blacklist.py` |

**时间窗口约束**：采集每天 09:00、体检每 2 天 22:00、周观点周一 08:00。迁移必须落在两个节拍之间的空档，且**每一步结束时都必须 `run.py check` exit 0 + `run.py export` 已同步**——半迁移状态被自动化撞上，就是一次真实事故。

## 八·为什么不建议一次做完

1. **收益不是均匀的。** P1（摘要契约）与 P3（口径单源）占收益的 8 成，而这两条**恰好由第一步 + 第五节的 `Result` 承担**。后面把 check 拆成 6 个模块、action 拆成 8 个文件，收益主要是「文件更小」，属于整容不是治病。
2. **风险不均匀。** 第三步要动 6 个 check 的**全部输出格式**，而体检提示词是照着现有格式写的（「取 `check_signals.py` 那一行的条数与退出码」）。摘要行逐字不变是硬要求，一旦哪天手滑改了措辞，体检的分类判断会整片失效——**这种破坏是静默的**。
3. **收益可以用别的方式先拿到。** 如果目标只是「不想记脚本名、不想改提示词」，那已经解决了（`run.py list` 读目录生成）。真正值得做的只有 `core` 拆分 + `Verdict` 枚举。

**所以我的建议是：只做第 1 步，做完停一周。** 一周后如果 `pkb/core/` 让改动的定位变快（今天这种「找 `summary` 在哪实现」的问题不用翻 312 行），再谈第 2～3 步；如果没感觉，就停在那里——**留着兼容层 `lib.py`，等于零风险**。

用户要求「按目标结构重构」，因此没有采纳第八节的「只做第一步」建议。**回滚点是 git**（工作区 `git init`，7 个提交：基线 + 五步），资料库未纳入版本控制。

| 1 | `lib.py` 312 行 → `pkb/core/` 五模块 | `check` 输出与基线逐行 diff 为空；`export` 后 docs 0 硬错误 |
| 2 | 口径 → `pkb/domain/` 四模块 | `grep -E "2026-W4[0-3]\|jiemian"` 只命中 domain |

| 5 | `tests/` **41 条**；`check_docs` 加口径单源扫描 | `pytest -q` 41 passed；注入 `'jiemian.com'`／`'2026-W40'`／`'科技与数字化'` 三条全部报错 |

**与本文档的偏离（三处，都有理由）**：

1. **没留 `lib.py` 兼容层**（第三节没写、第一步原文写了）。`import *` 会带出 3 条 pyflakes，「pyflakes 0」这条门槛从此失效；且两份导出清单本身就是新的副本源。15 个调用方一次性改成 `from pkb.core import …`，diff 全程可见。
2. **口径扫描的判据换成「AST 常量相等」**，不是「带引号的字面量」。逐行正则会把注释与 docstring 里的举例判成违规——第一版就把 `docs.py` 自己的说明判了 3 条。AST 只认真正作为值参与运算的常量；词典从 `pkb.domain.__all__` 现读，**不另写名单**（名单本身就是第二份副本）。
3. **本文档举的第三个例子「金融强国」抓不到**：它属口号类口径，库里没有任何 domain 归属，无处比对。要抓它就得在 domain 造一份口号名单，而那份名单没有任何代码在用——为通过一条验收而造一份死数据，比漏掉这个例子更糟。已在 `check_docs` 的 docstring 写明补救路径：将来要有规则认口号，先在 domain 声明，扫描自动覆盖。

**远程（当日补完）**：`git@github.com:purplefire1987/policy-analysis.git`（私有）。SSH 密钥无口令、公钥贴账号级 SSH keys 后 `ssh -T` 通过；远端 auto-init 的 `README.md` 与本地同名，用 rebase 把 11 个本地提交接到它之上（唯一冲突，两版合并保留），未强推、未丢远端历史。首次 `push -u origin main` 后 12 个提交、72 个文件、`git diff origin/main` 为空。

**为什么推送不用 MCP**：GitHub connector 令牌不能建库（403 `Resource not accessible by integration`），`push_files` 又只能落成单个提交、需把全部文件内容过一遍上下文——445 KB 的仓库走它既贵又脆。MCP 的位置是「读一两个文件、提 issue/PR」，不是搬仓库。
