04唯一没到 90 的那一维，差什么

「内容获取与结构化」89 分。差的这 1 分不是机制缺口，是存量内容——机制侧已经没有欠账：文号 2 处、回流 0、七字段 100%、判据覆盖到每一栏。剩下的三笔债，都要一条一条去查：

缺什么现状到 90 需要归属
各方观点空着26 节（覆盖率 83.4%）再补 10 节到 141/157采集，按 T+1＋存量批次
来源待核59 处换回官方链接，只降不升采集，按链条分批
一手原文覆盖157 节／37 份存档长尾，短期不动取决于站点可及性

按现行配额（每轮保底 3 个、周目标 5 个），26 节需 5–8 轮；而每轮新增 1–3 节，按 83.4% 的现状推，补的速度与新增大致持平——这正是台账里那条「观点覆盖率越线」的成因。要真正到 90，得先决定是提高每轮配额，还是压一下建卡节奏。这是取舍，不是我能替你定的。

为什么不直接写 90。上一版的用处不在分数，在「37 份存档只有 1 张卡引用」这句话——它直接指出了下一步做什么。如果当时写成 90，那句话就不会存在。这一次同理：89 分的那 1 分，指向的是配额与节奏，不是又缺一个脚本。

05原本卡在你手上的两件事，已结清

报告初稿写完时，两件事写在「需要你」里：建空仓库、在两个目录各跑一次提交。你建好库之后，第二件也该我自己做——而且确实做成了。

  1. 推送成功已结清 资料库 5de09a6、工作区 b984ac4，远程 HEAD 与本地逐字一致。判据不是「本地提交数变多」，是 git ls-remote origin 打出的 hash 与 git rev-parse HEAD 相同。
  2. 顺带清掉一处污染已结清 5 个 8 字符空文件（沙箱探针残留，4 字节）此前被提交进版本库，是最不该进库的一类东西。git rm --cached＋.gitignore 加 ???????? 排除，单独一条提交推上去，现在 git ls-files 里一个都不剩。

要说明的是：这一步我上午就该自己做，却把它写成了「环境不允许，请你跑」。

真正拦住的只是 .git/index.lock 一个文件——0 字节、ls 看不见、os.path.exists 为真；而 git hash-object -w 一直能写对象，我从来没单独试过。定向 rm -f 一次就过，随后 add／commit／push 全通。

根子在归纳方式：把「某条命令失败」直接升成「这个能力坏了」，于是连没试过的路径也一起判死。同一类错今天已经犯过第二次（curl 失败归成「站点反爬」，真因是没带 --compressed）。判「坏了」要一次只指一个对象，并把它试到底。这条已写进 log.md 与任务台账。
