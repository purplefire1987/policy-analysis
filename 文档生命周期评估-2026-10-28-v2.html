最值得记的一件事：判据把正确的做法判成了错误。 第一版给 check_vcs 写的判据是「raw/articles/ 被跟踪就是排除规则失效」。几小时后我决定把它纳入 git——因为实测每份平均 12.7 KB、全部 544 KB，而第一版说它「体积远大于其余全部」，那个数字没量过。

判据立刻报红。改法不是改判据迁就结论，而是换一个更准的问题：「.gitignore 声明要排除的，实际有没有被跟踪」（git ls-files -ci）。规则住在 .gitignore 里，判据只核对声明与事实是否一致。

同一类错误在库里已经出现过一次：模板写了「文号」栏却没人写过，而 check 九项一直全绿。判据记住的如果是某一个具体决定，那个决定一改，判据就开始说反话。

安全合规与审计 88 / 100

做到了

  • 新增 check_vcs（有无历史／声明的排除是否生效／久未提交）与 history（某文件改过几次、某条口径哪次改的）

  • CI 只在空库上跑 pytest，不跑真库体检

自动化与 AI 增强 90 / 100

做到了

  • 告警接进了 check：全量跑完自动按「要处置／要知道」两档写 wiki/总览/告警.md，并在终端打前几条。三个自动化本来就会跑 check，因此没有改一行提示词就获得了告警
  • 告警复用 check 已跑出的结果，不重跑十项；--only 时不写——结果不全，写出来会把其他问题从页面上抹掉
  • status 直接给出「数据截止：当天／不是当天」，后者明确要求报告标注截止日
  • 原来的 preflight 归并进 status：一条只在该用的时候才想得起来的命令，等于没有

  • 失败仍不会主动通知：告警页是异步的，得有人去翻
  • 三个自动化之间没有超时／重试约定，一个挂住另一个照跑
  • 告警的「要知道」判据靠摘要行里的关键词（0 新增 等），新写一种措辞就可能漏判

  • 生命周期靠 ledger 推，但归档副本是否完整仍要手工核

03到 90 分还差什么

剩下这 5 分，不是我改几行代码就能拿到的。三件事各有归属，第 1、2 件卡在你手上。

  1. 给资料库配一个远程仓库并首次推送需要你 这一步能把「安全与审计」从 88 推到 95 以上，也是全库唯一还把「本机一份」当备份的地方。建议新建一个只放资料的私有仓库（如 policy-vault），git remote add origin … 后 git push -u origin main。不要和现有的 policy-analysis 共用——那是另一段历史，硬合会重排提交线。若 SSH key 没加到账号，换 HTTPS + token 也行。
  2. 决定 4 张超限卡怎么处置需要你点头 金融、出口管制、医疗健康、对外贸易四张卡都在 27K–34K 字符。可选：旧政策小节整节移进 归档/ 并在卡里留一行索引，或者原地压缩、只留结论与链接。前者动结构（AGENTS 要求先问），后者不动结构但会删内容。你选哪个我照做。
  3. 剩余 11 个文号 + 71 处来源我可以继续 文号要逐条回部委官网核，每条至少两处独立来源；「国防动员法」那条建议先核卡片本身记得对不对。71 处来源换官方链接更慢，但可以按政策链分批。这两项做完，「内容与结构化」能到 92 左右。

为什么不直接写 90。这份评估的用处是让人知道哪里还能塌，不是拿来自我感觉良好的。第一版 75.3 分里最值钱的一句是「37 份存档仅 1 张卡引用」——它直接指出了下一步做什么；如果当时写成 90，那句话就不会存在。

上面三件事全部做完，这个库确实是 90 分水平。其中两件取决于你。
